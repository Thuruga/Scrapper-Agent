## Design System

| Property | Value |
|----------|-------|
| Tool | none — hand-rolled plain CSS with CSS custom properties (no Tailwind, no shadcn, `components.json` absent) |
| Preset | not applicable |
| Component library | none (custom `.glass-card` / `.btn` / `.input` classes in `frontend/src/App.css`) |
| Icon library | `lucide-react` |
| Font | `'Inter', system-ui, sans-serif` (source of truth: `frontend/src/App.css` `:root` + `body`) |

**Token-source finding (important — corrects orchestrator brief):** The app has two `:root` blocks — `frontend/src/index.css` (loaded first, by `main.tsx`) and `frontend/src/App.css` (loaded second, by `App.tsx`). Both declare the same custom-property names but with **different values**, and since `App.css` is imported after `index.css` with equal selector specificity (`:root`), **`App.css`'s declarations win the cascade and are what actually renders**. `index.css` also references `'Outfit'`/`'JetBrains Mono'` fonts that are never linked in `frontend/index.html`, so they silently fall back — `App.css`'s explicit `'Inter', system-ui, sans-serif` is what the browser actually paints. All tokens below are taken from `App.css` (the live values), not `index.css`. Do not use `index.css`'s `--accent: #8b5cf6` or `--bg-dark` names in new code — use the names/values below.

## Spacing Scale

Declared values (must be multiples of 4, mapped to the existing rem-based scale already in use):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (0.25rem) | Icon gaps, badge padding, inline gaps (`.monitor-badge`, `.badge-discount`) |

- Icon-only touch targets (`.btn-icon`, monitor row action buttons) must stay at minimum 40x40px hit area even where the visual icon is 16-20px, to preserve tap accessibility on the 768px tablet fix (UX-01). This mirrors the existing `.brand-chip` `min-height: 40px` convention.
- CEP/SKU inline validation text (`.cep-helper`) uses `4px` top margin and `12px` (0.75rem) font-size — smaller than the `md` body scale; this is an existing established exception, keep it for the new SKU inline error (reuse the class, do not invent a new one).

## Surface-by-Surface Contract

### 1. Responsive fix — category monitor + category sweep at 768px (UX-01)

**Root cause (confirmed in code):** `.grid-category` (`frontend/src/App.css:366-370`) is a fixed `350px 1fr` two-column grid with **zero media-query breakpoints** — unlike `.search-main-row`/`.search-control-row`, which already collapse to `1fr` at `max-width: 980px` (`App.css:1052-1057`). This is the layout used by both the category-monitor page (`MonitoredCategoriesPage`) and the category-sweep page (`CategoryPage`), so both inherit the overflow bug at 768px.

**Contract:**
- Add a `@media (max-width: 768px)` rule (colocate near the existing `980px`/`640px` blocks, `App.css:1052-1133`) that sets `.grid-category { grid-template-columns: 1fr; }` — sidebar-style 350px column stacks above the content column.
- Verify `.modal-content` (`App.css:1150-1158`, `width: 90%`, `max-width: 520px`) does not need changes — it already scales down; the products modal override (`max-width: 1200px; width: 95%`, `App.tsx:2944`) must also be checked for horizontal overflow at 768px — if the `gridTemplateColumns: 'repeat(auto-fill, minmax(250px, 1fr))'` product grid (`App.tsx:2983`) causes overflow, reduce `minmax` to `minmax(200px, 1fr)` at ≤768px via a scoped class, not inline style duplication.
- `.brand-selector-grid`/`.search-brand-grid` inside the category flows already wrap (`flex-wrap: wrap` / `grid-template-columns: repeat(2, ...)` at 640px) — no change needed there.
- Acceptance: at exactly 768px viewport width, no horizontal scrollbar on `.grid-category`, no element overlap, category tree/brand list column stacks above (not beside) the results column.

### 2. Price-monitor list promo value (UX-02)

**Gap (confirmed in code):** `.monitor-pricing` in `MonitorPage` (`App.tsx:417-434`) renders only `m.last_price` via `.monitor-price-value` — it never reads `m.price_discount`, even though the identical `price_discount` field is already rendered correctly two other places in the same file (`App.tsx:1658-1671` search results, `App.tsx:2999-3018` category monitor products).

**Contract:**
- Reuse the exact existing pattern from `App.tsx:3009-3018` (no new CSS classes): when `m.price_discount > 0`, render a `price-original` strikethrough span (`textDecoration: 'line-through', color: '#999', fontSize: '0.85em'`) showing `R$ {(m.price_full + m.price_discount).toFixed(2)}` immediately above/beside the existing `.monitor-price-value` (which becomes the promo/current price).
- Field name check: monitor objects use `last_price` as the display field today (not `price_full`) — the executor must confirm whether the monitor payload also carries `price_full`/`price_discount` (same shape as scan products) or whether `last_price` already equals the discounted price and a parallel `last_price_full`/`last_price_discount` pair must be read instead. Do not assume the field name without checking `backend/services/price_monitor_service.py` and `backend/data/price_monitors.json` shape — this is a backend-contract question, not a visual one.
- No new network call — the value must come from the same monitor list payload already fetched.
- Layout: keep `.monitor-pricing`'s existing `flex-direction: column; align-items: flex-end` — strikethrough goes above the bold current price, consistent with the product-card pattern (there it's a horizontal `flex` row; in the narrower `.monitor-pricing` column, stack vertically to avoid overflow).

### 3. Search-history access — top-right icon (UX-06)

**Gap (confirmed in code):** `HistoryList` currently renders as a full-width collapsible panel placed BELOW the search form (`App.tsx:1602` comparative, `App.tsx:2177` SKU/cross) — not "in the top-right corner" as required. It defaults `collapsed: true` internally (`App.tsx:781`).

**Contract:**
- Add a small icon-only button (`<History size={18} />`, `.btn-icon` class, no visible text) positioned top-right of each search tab's page header/card — sibling to (or inside) the existing `.content-header` (`App.css:230-235`, already `display: flex; justify-content: space-between`) so it lands opposite the page title without new layout primitives.
- Clicking the icon toggles the existing `HistoryList` panel's visibility (reuse `collapsed` state — lift it out of `HistoryList` internals if needed so the top-right icon can control it, or keep `HistoryList` self-contained and have the icon call its exposed toggle). Do not duplicate the history-fetching logic — same `ApiClient.getHistoryList()` call, same `HistoryList` component, only the trigger/position changes.
- Badge: when a filtered count > 0, show the existing small pill badge (`.monitor-badge`, `--primary` color, `rgba(99,102,241,0.12)` background, `2px 8px` padding, `20px` radius) as a corner badge on the icon button, mirroring the count badge already in `HistoryList`'s header (`App.tsx:854-856`).
- Applies identically to BOTH search tabs (comparative `App.tsx` ~1468 render return, and SKU/cross `App.tsx` ~2135 render return) — same icon, same position, same interaction; only the `type` prop passed to `HistoryList` differs (`'search'` vs `'cross'`).
- Acceptance: icon is visible without scrolling on page load, in the top-right of the page/card header, on both tabs.

### 4. SKU search — pattern validation + CEP same row (UX-07)

**Partial gap (confirmed in code):** CEP is ALREADY on the same row as the SKU input in `CrossMarketplacePage` (`App.tsx:2139-2166`, `display: flex; gap: 16px` inline style) — this matches the comparative search's `.search-main-row` grid intent, but uses raw inline `style` instead of the `.search-main-row`/`.search-field` classes the comparative tab uses (`App.tsx:1472-1524`). Missing piece: **no frontend pattern validation** on the SKU input (`App.tsx:2142-2150` is a plain `required` text input with no `pattern`/regex check or inline error).

**Contract:**
- Layout: migrate the SKU form's inline `style={{ display: 'flex', gap: '16px' }}` row to the same `.search-main-row` / `.search-field` / `.search-field-label` / `.search-input-wrapper` / `.search-input` classes already used by the comparative search (`App.tsx:1472-1524`), so both tabs share one visual row pattern and one responsive breakpoint (`980px` collapse to `1fr`, already defined at `App.css:1052-1057`) — this is a code-consistency requirement, not just a visual nice-to-have, since UX-07 explicitly says "igual ao layout da busca comparativa."
- Validation pattern: `^ML\.05\.\d{7}$` (matches placeholder `ML.05.0326046` at `App.tsx:2145` and requirement example `ML.05.0326046`). Validate on blur AND on submit (do not block keystroke-by-keystroke typing).
- Reuse the exact `.cep-input-error` / `.cep-helper` / `.cep-helper-error` visual pattern already implemented for the CEP field in the comparative search (`App.css:1281-1305`, `App.tsx:1489,1513-1522`): red outline ring on the input wrapper when invalid, small 12px helper text below with `AlertTriangle` icon (`size={12}`) when in error state, neutral helper text when valid/empty.
- Submit button (`App.tsx:2170-2173`, "Buscar em Marketplaces") must be `disabled` when the SKU fails the pattern check, mirroring how CEP errors already block flow elsewhere.
- Acceptance: typing a non-matching SKU (e.g. missing prefix, wrong digit count) and blurring the field shows the inline error copy from the Copywriting Contract; typing a valid SKU clears it; CEP field remains on the same row at all viewport widths above the `980px` collapse breakpoint.

### 5. Category monitor — auto-start first sweep (UX-08)

**Gap (confirmed in code):** `handleSubmit` in `MonitoredCategoriesPage` (`App.tsx:2673-2686`) only calls `ApiClient.createMonitoredCategory(newCategory)`, resets the form, closes the modal, and calls `fetchCategories()` (refreshes the list table). It never triggers a scan/sweep and never opens the results view.

**Contract:**
- After `ApiClient.createMonitoredCategory(...)` resolves successfully, immediately trigger the first sweep for the newly created category — reuse whatever backend action already exists for a manual/on-demand category scan (the plan/executor must confirm the exact endpoint; do not invent a new one if `ApiClient` already exposes a "scan now" call used elsewhere, e.g. near `handleViewProducts`/`getMonitoredCategoryProducts`).
- While the sweep runs, keep the modal closed (per requirement: "sem necessidade de clique em iniciar") but show a lightweight loading indicator on the newly-added row in the categories table (reuse `<RefreshCw className="animate-spin" size={14} />`, the same spinner already used for "Carregando árvore de categorias..." at `App.tsx:2911`).
- On sweep completion, the results must "aparecer na lista" — interpret this as: either (a) auto-open the existing products modal (`handleViewProducts`) for that category, or (b) update the categories table row's "Última Varredura" / status cell in place without requiring the operator to click "Ver Produtos" first. Given the existing `handleViewProducts` modal is the only place products render today, and UX-08's success criterion says "resultados aparecem na lista" (the categories table), prefer (b) as the minimum bar — update `last_scraped_at`/status in the table row — with (a) as an enhancement if trivial. Do not require a new products-list surface.
- Toast feedback: use the two new toast strings defined in the Copywriting Contract above (success / failure), following the existing `toast.success(...)` / `toast.error(...)` (sonner) pattern used throughout the app (e.g. `App.tsx:1972`, `2079`).
- Acceptance: after clicking "Salvar" in the add-category modal, no additional "Iniciar" click is required anywhere in the flow before the category shows scan results/status.

### 6. Lacoste removed from all brand-selector surfaces (COMP-08)

**Confirmed:** zero hardcoded `Lacoste`/`lacoste` string references exist anywhere in `frontend/src/` (grep returned no matches). Every brand-selector surface (comparative search brand chips `App.tsx:1581`, category monitor brand `<select>` `App.tsx:2882`, category sweep brand list) already renders purely from the `brands` prop/array passed down from the backend `list_brands()` response, with only a local `is_active !== false` filter applied client-side in one place (`App.tsx:1581`).

**Contract:**
- No frontend code change is required to hide Lacoste specifically — enforcement is entirely the backend chokepoint `list_brands(active_only=True)` (already the documented single point of truth per STATE.md `[ARCH]` decision). The UI contract here is a **non-regression guarantee**: no new brand-selector surface introduced or touched by Phases 38 work may special-case any brand by name, and no client-side filter may be added that duplicates or diverges from the `is_active` flag already used at `App.tsx:1581` (`brands.filter(b => b.is_active !== false)`).
- Audit note for the category monitor `<select>` (`App.tsx:2877-2885`) and the category-sweep brand list: confirm both also read from the same `active_only`-filtered `brands` array as the comparative search's chip grid — if either surface receives an unfiltered brand list (bypassing `is_active`), that is the actual bug to fix under COMP-08, not a new Lacoste-specific filter.
- No new copy, no new visual state — Lacoste (while `is_active=false`) simply does not appear as an `<option>`/chip, identical to how any other deactivated brand already behaves today.
- Acceptance: with Lacoste's `is_active=false` in `backend/data/brands.json`, it does not appear in the comparative-search brand grid, the category-monitor "Marca" select, or the category-sweep brand list — verified by the regression test named in ROADMAP Phase 38 success criterion 6 (backend-side, `list_brands(active_only=True)` coverage — no frontend test required beyond confirming no special-case code was added).
