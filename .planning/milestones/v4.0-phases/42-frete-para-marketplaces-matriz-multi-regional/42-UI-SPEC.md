## Spacing Scale

Declared values (must be multiples of 4, mapped to the existing rem-based scale already in use — unchanged from Phase 38):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (0.25rem) | Icon gaps, badge padding, region-row inline gaps |
| sm | 8px (0.5rem) | Compact element spacing, button icon gap, `.shipping-controls-bar` gap |
| md | 16px (1rem) | Default element spacing, modal internal spacing, matrix table row padding |
| lg | 24px (1.5rem) | Section padding (`.modal-content` padding — reused as-is for the Matriz Regional modal) |
| xl | 32px (2rem) | Layout gaps (not used directly by this phase's new surfaces) |
| 2xl | 48px | Major section breaks (not used) |
| 3xl | 64px | Page-level spacing (not used) |

Exceptions:
- Icon-only touch targets (the new "Matriz Regional" button when rendered icon-only in the cross-marketplace card, matching the existing "Calcular Frete" button footprint) must stay at minimum 40x40px hit area — same exception already established in Phase 38 for `.btn-icon`.
- Matrix table region rows on narrow viewports (≤640px, mirroring `.shipping-options-list` breakpoint at `App.css:1430`) may reduce horizontal padding to `8px` to avoid overflow — same pattern already used for `.shipping-option-row` wrapping.

## Surface-by-Surface Contract

### 1. Marketplace shipping cost+time rendering (FRET-08 UI surface)

**Gap (confirmed in code):** The cross-marketplace card at `App.tsx:2503-2531` currently renders only `shipping_price`/`is_free_shipping` — there is no rendering path for delivery-time text, and no `blocked` state at all (the only states handled today are "calculating" and "price known").

**Contract:**
- When `shipping_options`/enriched item data includes an estimated delivery-time field (mirrors the VTEX/Wake/Shopify pattern: `estimate_display` / `raw_text` / `estimated_delivery_days`), render it as small muted caption text (13px, `--text-muted`) directly beneath or beside the price line, reusing the same field-fallback order already implemented at `App.tsx:1814` (`opt.estimate_display || opt.raw_text || (opt.estimated_delivery_days ? \`Até ${opt.estimated_delivery_days} dias úteis\` : '')`). Do not invent a new fallback order.
- When the marketplace/engine returns the new `blocked` state (Netshoes, per D-01), render the verbatim "Bloqueado (anti-bot)" string in `--error`, replacing the "Calcular Frete" button for that item (mirrors `.monitor-price-blocked` exactly — a static labeled state, not a retryable button, since blocked is a known/permanent-for-now condition, unlike `temporary_failure` which keeps its "Tentar novamente" affordance per the existing `App.tsx:1855-1867` pattern).
- No new button is created for "custo+prazo" — this is inline enrichment of the existing "Calcular Frete" flow at `App.tsx:2507-2526`/`handleCalculateShipping`, per D-05.
- Acceptance: a Mercado Livre or Amazon item with a successful shipping calculation shows both price and prazo text without layout shift or overflow in the existing card; a Netshoes item shows "Bloqueado (anti-bot)" instead of a spinner-then-nothing.

### 2. "Matriz Regional" action (FRET-09 UI surface)

**Insertion points (per D-06, confirmed in code):**
- Busca comparativa / SKU: adjacent to the existing `.shipping-calc-btn` "Calcular Frete" button, `App.tsx:1766-1780`.
- Cross-marketplace: adjacent to the existing "Calcular Frete" button, `App.tsx:2507-2526`.

**Contract:**
- Render a second button, visually consistent with (but distinguishable from) "Calcular Frete": same outline style, `<MapPin size={14} />` icon, label "Matriz Regional". Place it directly beside the existing button — same flex row, `8px` gap (`sm` token) — never replacing or hiding the single-CEP button (D-06 explicit: "ao lado... Não criar um painel/tela dedicada nova" and "frete simples... e matriz... continuam sendo ações distintas").
- **Always visible** per D-07 — including for engines with no shipping provider at all (SFCC) and for engines expected to fail all 5 regions (Netshoes). Do not gate this button behind `isBrandShippingSupported`/`isVtex && p.sku_id` the way "Calcular Frete" is gated (`App.tsx:1765`) — the Matriz Regional button has no eligibility gate; every product row gets it, and the resulting modal communicates the real per-region state (available/blocked/unsupported/temporary_failure/unavailable_for_cep).
- **Layout chosen: modal**, not inline table or tooltip. Rationale: 5 regions × (cost + prazo + state) is too much structured content for a tooltip (accessibility risk, no room for retry affordances) and too much to inject inline into an already-dense product card without disrupting the grid (Dimension 5 spacing risk). A modal mirrors the existing, already-approved CEP-input modal pattern (`App.tsx:2564-2609`) exactly — same `.modal-overlay`/`.modal-content` classes, same `max-width` treatment (use `480px`, between the CEP modal's `420px` and the default `520px`, to comfortably fit 5 rows of region+price+prazo+state without feeling oversized).
- Modal content structure (top to bottom): heading "Frete por região" + close button (mirrors `App.tsx:2568-2571`) → one-line helper subtitle → 5 rows, one per region in a fixed order (Sudeste, Sul, Centro-Oeste, Nordeste, Norte — matches `cep_matrix.json`'s curated order) → no footer action needed (read-only result view, "Fechar" is the only action).
- Each region row shows: region name (bold, 14px) + CEP (muted, 13px, e.g. "01310-100") on the left; on the right, one of the state renderings defined in the Copywriting Contract above (available/blocked/unsupported/temporary_failure/unavailable_for_cep). Reuse `.shipping-option-row` as the base row class (already handles the label-left/price-right flex layout and the 640px wrap breakpoint) rather than inventing a new row class.
- Loading: while the 5 region calls are in flight, each row (or the whole modal body) shows the existing `.shipping-loading` spinner+"Calculando…" pattern. Given Open Question #2 from RESEARCH.md is left to this contract's discretion: show all 5 rows in a loading state simultaneously (not sequential reveal) — simpler to implement, avoids a confusing "some rows done, some still spinning" impression, and does not violate D-07's "always attempt" requirement since the resolver-level `UnsupportedShipping` short-circuit (if implemented by the planner) still resolves near-instantly and simply renders its final state faster than the others, not as a separate visual mode.
- Acceptance: clicking "Matriz Regional" for any product (VTEX, Wake, Shopify, ML, Amazon, Netshoes, or an unsupported engine) opens the modal and, within a reasonable time, shows exactly 5 rows each in one of the defined states — never a blank row, never a silently-hidden region, never a fake `R$ 0,00`/free-shipping value substituting for a real unresolved state.
